What is consistent

All 113 plotted worst errors, raw minima, median errors and median/minimum/maximum times reconstruct from their linked records. All primary accuracy and timing source digests match the chart. The 107 models eligible for recommendations share the same declared input fields, including base pressure, residual, reference pressure and RHS, with matching per-field hash metadata. The audit inspected 734 hash-bound artifacts and verified the retained weights for 108 models; their tensors are float32. Captured architecture metadata establishes float32 networks and float64 pressure for 112 models, including every ranked model. The older C02 architecture was not recovered by this audit.

C01–C06 use other populations and are correctly excluded from Pareto recommendations. They can still appear under All cohorts, so that view is not one common benchmark. C01/C02 each use 32 early development snapshots; C03–C05 use 12 snapshots; C06 uses 128 different reserved-test snapshots.

What is inconsistent or missing

  1. Timing procedure: 69 points use single-sweep chart diagnostics, 42 use managed restore/test prediction exports, and two use early retained prediction timings. There is no chart-wide warm-up, repetition, randomized order, or uncertainty standard. These are categories of measurement, not four identical controlled protocols.
  2. Runtime settings: 73 timing records observe one PyTorch thread; 69 explicitly record CPU affinity [23]. Forty omit observed thread counts and 44 omit timing affinity. Package versions are absent from 70 timing records, including all 69 chart diagnostics. Known versions are 2.8.0+cpu for three early, unranked points and 2.14.0+cu132 for 40 points. A CUDA-enabled package label does not mean that these CPU measurements used a GPU. The record does not establish identical CPU hardware, frequency state or background load across the historical campaigns.
  3. Execution context: the current chart builder uses torch.no_grad(), whereas the repeated calibration benchmark uses torch.inference_mode(). Twelve diagnostics match the current builder hash; the 57 other historical diagnostic builder bodies were not recovered here. Their exact context is not promoted from an assumption to an observed setting.
  4. Inference work: 25 models declare one fine CNN stage, 82 declare two, and five declare four; C02 is unresolved. Learned coarse/shape/tail heads can add work beyond those CNN-stage counts. The scatter times one complete pressure proposal, not a common number of network forwards, and it does not compare cost to a common achieved accuracy. Training-pass counts and names such as “four-pass teacher” are not deployment pass counts.
  5. Accuracy evaluator: 69 chart diagnostics measure the Python/Torch pressure-equation residual only; 44 older points use native verification of saved predictions. This audit verifies recorded values and input identities, not a fresh cross-backend numerical parity run for every checkpoint. Physical pressure/velocity/tracer quality and solver acceptance are not represented by the single Y value.
  6. Statistics: X is median time across heterogeneous domains; Y is the worst error across them. They need not describe the same request. Best/worst inference times are across different inputs, not confidence intervals from repeated timing. Strict Pareto membership can change because of small timing fluctuations or negligible error differences.

How much does this represent real use?

It answers: how fast does one captured AI pressure-prediction call run on an already prepared, small, saved CPU input, and what is its worst equation residual on this dataset?

It does not include loading/setup, engine-to-model sample preparation or transfer, the surrounding fluid integration, native pressure acceptance checks, or additional adaptive corrections needed to meet the final accuracy target. Operator/coarse-gate work inside the captured prediction is included. Some excluded work is necessary in production; it is not all development diagnostics.

None of these original proposals meets the chart’s 1e−6 equation target on every case. That is not a verdict on their iterative deployment policies: those are separate measurements. It means the scatter cannot establish end-to-end pressure-solver speed, simulation throughput or equal-quality speedup over Rheon. It also cannot establish long-horizon drift or multi-frame generation performance.

Cold geometry preparation, warmed steady-state calls, fresh input populations, 32³ and larger domains, and model-driven accepted trajectories require separate results. They should not silently replace one another in a single speed ranking.

Recommended comparison standard

  1. Attach an explicit protocol ID to every measurement: exact weights and captured execution policy, input hashes, CPU/model, package/build versions, threads/affinity, dtype, PyTorch context, batch size, and cache/setup rules. Recommend models only within a common protocol.
  2. Remeasure all ranked fits in one balanced serial campaign: one declared production inference context, full-population warm-up, randomized case order, at least five rounds, and recorded spread. Keep cold setup as a separate measurement.
  3. Retain per-domain timing and error. Plot grid size and grid density separately; use an explicit deployment-weighted aggregate rather than assuming this 64-domain mix represents production.
  4. Provide two clearly named comparisons: original-proposal quality/cost and total pressure-solver cost to the same accepted physical accuracy. Measure complete native fluid steps separately, including necessary integration/bridge work.
  5. Use independent scenes and long model-driven trajectories for generalization and drift claims. Keep the six early populations outside current rankings, and show numerical measurement uncertainty when drawing the frontier.

These are recommendations. This audit has not replaced plotted times, rerun inference or changed the chart’s rankings.
