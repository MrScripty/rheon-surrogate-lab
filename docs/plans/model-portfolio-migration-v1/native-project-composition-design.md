## Binding behavior and ownership

The working project is the primary editable source. Preserve every revision of
its adopted notes, graphs, definitions and measurement sources; create the new
editable identities through the existing independent-fork owners. All original
source envelopes remain inert and origin scoped. Secondary editable drafts and
operation receipts remain archived instead of becoming active accidentally.

Identical canonical envelopes share one representation. A same-ID conflict is
rejected except when two Run histories are byte identical outside the grant and
consumption portions of their admission proof, including an identical admission.
Retain the primary envelope unchanged and the complete alternate document as a
native `run_observation`. Each source membership identifies which representation
recovers its exact original envelope. Both proofs still pass the native history
owner; neither creates a disclosure or execution permission. The four overlaps
remain four Runs, rather than eight.

Use a native `project_composition_v1` provenance record for the ordered source
project/checkpoint identities and complete membership hashes. It owns provenance
only. Its decoder verifies every retained representation against the membership
hash, rejects dangling/extra observation mappings, and binds the primary source
to the destination's ordinary fork overlay. Historical roots and paths never
become filesystem capabilities. Register the new family with its decoder and
archive it during later forks; existing project formats retain their meaning.

The independent-project publication owner retains the current no-overwrite
stage/commit/rename lifecycle. Extend its source set explicitly; do not duplicate
that lifecycle in a migration script. The composition owner supplies merged
originals and primary editable forks. Domain owners validate every input and the
complete destination. The artifact owner verifies source declarations, rejects
corruption, conservatively promotes shared unique bytes, and copies each required
content identity from an explicitly verified source. Missing regenerable runtime
dependencies remain explicit; no unique byte may be omitted or regenerated.

The workspace owner supplies authorization, quiescence, clean primary working
files, source checkpoint guards, configured-root capabilities and resource
cleanup. A native composition operation may be advertised only once this whole
path exists. Use the existing owner-client contract negotiation and retain one
request before dispatch. Reconciliation uses the exact request identity and
native publication receipt; a timeout never causes a new-key replay.

## Composed-design admission

Applicability: applicable, because composition adds durable multi-source
provenance and extends a native publication lifecycle.

1. Independent concerns: composition decides retained identity/provenance during
   candidate construction; history owns Run/proof meaning; fork domain owners
   create editable descendants; artifacts own byte custody; store/fork publication
   owns durable filesystem transitions; workspace owns current authorization and
   quiescence. Each remains at its existing native boundary for its own reason.
2. Required interleavings are exact source identity/checkpoint checks around
   copying and publication, plus current workspace guards. Historical actor IDs,
   runtime paths and controls are retained values, never current authority. Avoid
   an accidental second SQL authority or script-owned publication lifecycle.
3. Callers supply explicit source selections, destination and one request key.
   They do not choose conflict winners, reconstruct admission proof shapes, copy
   individual payloads, or know canonical revision filenames. The workspace root
   knows configured roots; pure composition does not.
4. A new Run-proof format changes the history decoder/capture owner and, only if
   conflict policy changes, composition. A new editable family changes its fork
   owner and archive registration. A filesystem durability change stays in the
   publication/store owner. A new migration card changes project content only.
5. Stable interfaces carry snapshots, declarations and source membership hashes.
   Root descriptors, locks, operation ordering and request receipts stay inside
   workspace/publication. Cross-owner persisted representations have explicit
   formats; no decoder trusts an old path as a live capability.
6. Pure source assembly is tested without SQL/filesystem execution. History
   observation capture uses native codec/SQL tests. Publication has real filesystem
   failure/reconciliation gates; the owner operation and final UI are separate
   path claims. A failure preserves input checkpoints and retained staging.
7. Removing the composition owner scatters conflict/provenance policy into
   callers; removing native provenance loses exact source reconstruction.
   Removing a second migration-only copier removes accidental complexity, so no
   such permanent copier is admitted. Existing fork/artifact/store owners remain.
8. Inherent complexity is multiple source identities, alternate historical
   proofs, source freshness and independent payload custody. It is contained in
   one composition owner plus existing lifecycle owners. No model execution,
   credential transfer, solver upgrade or new training pipeline is introduced.

The target is the task-owned Tuldok integration line; `/root` owns this private
branch and serial integration. Retain its clean worktree while publication is
implemented and qualified. Integrate the complete accepted proposal without
rewriting shared history, then retire redundant worktrees only with retained-ref
and live-controller checks. No remote push or original-service switch is implied.
