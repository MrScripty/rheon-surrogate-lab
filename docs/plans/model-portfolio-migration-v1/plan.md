## Decisions and boundaries

1. **Reference epochs.** Preserve the exact existing solver binaries, dirty
   source changes, runtime identities, data manifests and recordings. Commit IDs
   alone do not identify locally modified builds. Old and new Rheon outputs
   belong to different reference epochs. Porting a scene to new Rheon produces
   new data; it cannot silently replace an old training target.
2. **Complete coverage.** Include trained checkpoints, failed and unpromoted
   fits, unfitted prototypes, compositions and execution variants. Discover
   uncharted models through retained receipts and artifacts, not just the HTML
   dashboard. Deduplicate identical weights without losing aliases or distinct
   execution behavior. Every discovered entry gets a disposition and evidence;
   missing artifacts remain visible work, not silently excluded models.
3. **Task appropriate comparison.** Pressure-only models and complete state
   generators have separate benchmark contracts. Compare a model on every case
   supported by its declared contract and retain explicit unsupported cases.
   Do not change its architecture to make it enter a comparison. Every model
   must receive its full applicable benchmark; the two quoted examples are
   initial regression anchors, not a substitute for the portfolio run.
4. **Fair measurements.** A comparison identifies the reference epoch, exact
   cases and starts, grid dimensions, cells per metre, timestep, K, outputs,
   metric definition and normalization, device, precision and timing scope.
   Separate per-case results from population worst errors. Keep pressure,
   equation, velocity and tracer errors distinct. Rank only compatible groups.
5. **Simulation work.** A K-output block advances K whole output intervals.
   Record its total physical duration, actual internal advances, pressure
   projections and shared computation. A variant name such as N8 is not a
   measurement of work performed. Output cadence is not forcing frequency.
6. **Resources.** GPU timings are labeled GPU and include complete field
   generation, ownership, transfers and synchronization for full-state models.
   Retain setup, compilation and cold-call costs separately from warm samples.
   Every new learned constructor, probe, restore and inference executes on CUDA.
   CPU data decoding, normalization, prescribed controls and scoring are allowed;
   retained CPU probes and reproducibility protocols do not authorize new CPU
   neural forwards. Device and thread counts remain explicit.
   Rheon simulation workers together use at most half the physical CPU cores;
   benchmark timing does not overlap controlled training or reference capture.
7. **Native Tuldok ownership.** Use the fetched application's external project
   format, scientific data views, exact evidence comparisons and Experiment
   progression. The deliverable is a project directory anchored by
   `projects/rheon-model-portfolio-unified-04/.tuldok/project.json`, created through its
   owner operations. It includes canonical text records and project scripts;
   generated payloads live in ignored artifact storage. A copied dashboard or
   hand-authored substitute manifest is not completion.
8. **Truthful history.** Preserve original results, failures, timestamps and
   execution provenance. Retrospective descriptions and lineage are labeled.
   Record derivation only when supported; a comparison baseline is a different
   relationship. Never turn an imported historical result into a fabricated
   fresh Run or an execution grant. Missing historical intent is distinguished
   from a documented retrospective interpretation of the code.
9. **One coordinated migration.** Select the old project through its current
   owner and preserve existing retained snapshots and custody receipts. Do not
   create identical backup files or copies of datasets, weights or projects.
   Use supported extraction into separate installation control storage, account
   for every selected record/artifact, and retain original failures. Do not add
   a permanent second catalog or legacy reader. Historical import never
   activates old credentials, filesystem bindings or approval records.
   Retain scalar per-case results and summaries, rather than bulk forecast
   arrays. Generated fields are transient in memory for independent scoring,
   ownership checks, hashing and transfers; discard them afterward. Preserve
   training/reference data, model weights and model-setup assets. Historical
   prediction files retire only after their scalar results and identities are
   accounted for. Field-array custody is superseded by this user instruction.
10. **Source and retention.** Preserve unrelated dirty work, especially Rheon's
    unresolved primary merge. Inspect upstream versions in isolated worktrees.
    Inventory local changes before deciding what is already upstream, still
    necessary, superseded or obsolete. Any required software changes follow
    the coding standards MCP and have focused verification. No model weights,
    simulation arrays, executables, compiled libraries or database files are
    added to Git. No weight deletion is authorized in this phase.

## Composed design review

Applicable: this work crosses model, reference, execution, project persistence
and visualization owners.

1. **Concerns.** Rheon owns reference physics and generation. The lab owns model
   execution, scientific metrics and reproduction. Tuldok owns project records,
   Run custody, lineage and views. Operators own host bindings and runtime setup.
2. **Interleavings.** Old capture and benchmarking precede new-solver adoption.
   Historical import precedes project accounting; current execution requires
   fresh local authority. Chart labels and filesystem locations never choose a
   solver, metric or parent.
3. **Caller knowledge.** A benchmark caller supplies a declared model adapter,
   immutable case selection and device/timing contract. A project importer
   supplies scientific records through supported owner operations; it does not
   edit Tuldok SQL or synthesize material/custody documents.
4. **Change locality.** A checkpoint changes model identity and measurements. A
   new solver changes the reference epoch and generator. A UI change changes
   native projections. None requires rewriting old scientific facts.
5. **Dependencies.** Stable references carry source, case and metric identities.
   Version-specific adapter and one-time extraction knowledge stay at their
   respective boundaries, not in every card or graph.
6. **Independent replacement.** Old inference remains runnable while a new
   Tuldok project is tested. New Rheon generation is qualified independently
   after the old result archive is complete.
7. **Deletion test.** The inventory is a migration/reproduction input, not a
   second ongoing catalog. Removing it after migration must not remove native
   project facts. Existing Tuldok ownership contains persistence, lineage and
   visualization; no new service or replacement dashboard is needed.
8. **Inherent complexity.** Different model tasks and reference epochs require
   explicit adapters and comparison groups. A small lab runner owns that
   variation; native project records expose concise scientific explanations.
