# Roadmap: from pressure models to a general, real-time fluid solver

**Status:** approved 2026-11-19. Decisions: merge the lab, Tuldok and Rheon into `main` through pull requests, deleting each branch on merge; the earlier-study records leave the tree, with a one-page history ([docs/history.md](../docs/history.md)); the new Rheon is GitHub's; the playground is a web page (later, once something fully works, it can run in the browser on GitHub Pages). Compute for dataset generation and training still needs the owner's word.

**Owner, 2026-11-19 (in short):** clean the repository; a simple example app that runs a model in real time in a configurable domain where a force can be placed; a general fluid solver (fluids defined by their properties, not only water); several fluids in one domain (water and air, splashing); boundaries that are not hard walls (open water, inflow and outflow, wrap-around); forces of many kinds, not only sinusoidal, and several per scene; a dataset that is well defined and not redundant, within 24 GB of VRAM; the new Rheon for all new data and models, the old data kept for the old models; Rheon's book rewritten principles first, like Kenoma's; two branches of models, accuracy (engineering) and speed (games, a Godot plugin later).

## Where things stand (2026-11-19)

- **The models that exist** (206, all trained in October) are **pressure models**: inside Rheon's step they replace the pressure solve. The best balance on the frontier is about **6–7 ms per GPU pressure call**, measured over 128 requests on **sealed 16³–40³ boxes of water** (no free surface, no air, no obstacles, no open boundaries). The rest of the step (advection, forces) is Rheon on the CPU, so 7 ms is not the time of a whole step.
- **Whole-step models exist too** (corrected 2026-11-19): 35 **full-state generators** take the whole state and produce the next one on the GPU, from 0.8 ms per 1/60 s step (velocity error about 9 %) to 5.3 ms (about 2·10⁻⁶) on grids up to 32³. The solver's arithmetic as a fixed GPU network (the "F64 composition") is faster still (0.25–0.6 ms per step) and more accurate on these sealed boxes, so learned models only pay off where the solve is expensive: large grids, free surfaces, several fluids, obstacles. The lab's `surrogate/` package has a divergence-free 3D U-Net stepper, its training loop and a benchmark runner, written and unit-tested, never trained (no compute was approved). The playground can start with the existing generators and the F64 composition.
- **Forcing in the data is sinusoidal** (the "sinusoidal development rollouts" and the diversity windows vary amplitude, frequency and shape, but not the kind of force).
- **The data behind the existing models is kept**: 25 datasets' files and 203 models' outputs are in Tuldok's project directory on this machine (16.9 GB), and the solver that made them is pinned: Rheon branch `lab/reference-solver-v1` (`bbe01bd3`, on GitHub), referenced by `probes/reference/`. The 12 long development trajectories and the 52 reserved diversity scenes were never written to disk.
- **The lab repository**: the Tuldok project is moved to the new format (`projects/surrogate-lab/`, checked clean: 0 errors). Not yet cleaned up:
  - the old-format project code and file (`tuldok/`, `tuldok-project.json`);
  - an old-format rehearsal project (`projects/rheon-measurements-rehearsal-01/`, untracked);
  - a stale agent handoff (`handoff.md`, untracked);
  - about 6,100 files of earlier-study records (`docs/plans/`, `experiments/`);
  - 54 local branches, including two backups that must not be deleted without the owner's word.
- **Rheon here** is at `bc2f4727` with an interrupted pull (a conflicted README and staged files). GitHub's newest is `origin/main` of 2026-10-22, 193 commits ahead. It adds material fluids, a liquid/gas particle preview, conservative liquid-volume transport, periodic transport, collision meshes and a research book.
- **Tuldok** has everything this plan needs on its side: live training views, sweeps, kept fields, Compare, curation by embeddings, serving. It is committed on `feat/definition-first-projects`, not pushed.

## The rule that keeps the data clean

Every dataset definition names its **solver generation**: `rheon-reference-v1` (the pinned `lab/reference-solver-v1`) or `rheon-v2` (a pinned commit of the new Rheon). The existing datasets and models stay `rheon-reference-v1` and are never retrained on, mixed with or benchmarked against `rheon-v2` data. Every new model uses only `rheon-v2` data, and each generation gets its own benchmarks. A Tuldok check refuses a recipe whose datasets mix generations. Comparisons across generations are made only on scenes both solvers can run, and are labelled as such.
